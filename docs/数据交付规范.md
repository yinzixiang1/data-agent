# NL2SQL 语义层数据交付规范

## 概述

每张表需要一个 YAML 语义层文件，放在 `semantic_layer/tables/<表名>.yaml`。

**推荐方式：用 Claude 先扫业务代码再扫 DDL，自动生成 YAML**，最后人工审核补充。

---

## 一、用 Claude 生成语义层

### Step 1: 扫描业务代码（提取枚举 & 业务逻辑）

> 这一步最关键。DDL COMMENT 通常只有简单注释，真正完整的枚举定义、业务逻辑、查询模式都在代码里。

在业务项目的代码仓库中，让 Claude 先扫描代码，提取与目标表相关的信息：

````
请扫描当前项目代码，提取与表 `<表名>` 相关的以下信息，整理成结构化文档：

1. **枚举定义**
   - 搜索 Java/Python/TS 的 enum 类、常量类、字典表
   - 重点关注该表各字段的枚举映射（值 → 含义）
   - 搜索关键词：表名、列名、列名对应的驼峰命名

2. **业务逻辑**
   - 该表在 Service/DAO/Repository 层怎么被查询的
   - 常见的 WHERE 过滤条件是什么（如 status=1, is_delete=0）
   - 常见的 GROUP BY / 聚合维度

3. **表关联关系**
   - 代码中出现的 JOIN，该表和哪些表关联，通过什么字段
   - MyBatis XML / JPA / QueryDSL 中的关联查询

4. **业务术语**
   - 代码注释、Swagger 文档、前端 i18n 中对各字段的中文描述
   - 业务侧对这张表数据的常用叫法

5. **敏感字段**
   - 代码中有脱敏处理、加密存储、权限控制的字段

请按以下格式输出：

## <表名> 代码分析结果

### 枚举定义
| 列名 | 值 | 含义 | 来源文件 |
|------|-----|------|---------|
| ... | ... | ... | ... |

### 查询模式
- 常见过滤条件：...
- 常见聚合维度：...
- 常见 JOIN：...

### 业务术语
| 术语 | 含义 | SQL 条件 |
|------|------|---------|
| ... | ... | ... |

### 敏感字段
- ...

### 来源文件清单
- ...
````

**Claude 会扫描的位置（以 Java 项目为例）：**

| 扫描目标 | 能提取到什么 |
|---------|-------------|
| `**/enum/**`, `**/constant/**`, `**/enums/**` | 完整枚举定义（值 → label） |
| `**/entity/**`, `**/model/**`, `**/domain/**` | 字段注解（@Column, @ApiModelProperty）→ 中文名 |
| `**/mapper/**/*.xml`, `**/repository/**` | SQL 查询模式、JOIN 关系、常用过滤条件 |
| `**/service/**`, `**/manager/**` | 业务逻辑、状态流转 |
| `**/controller/**`, `**/api/**` | 接口描述 → 业务术语 |
| `**/i18n/**`, `**/messages*.properties` | 中文翻译 |
| `**/vo/**`, `**/dto/**` | 字段中文描述（Swagger 注解） |

### Step 2: 导出建表 DDL

```sql
SHOW CREATE TABLE <表名>;
```

### Step 3: 生成 YAML

将 Step 1 的代码分析结果 + Step 2 的 DDL 一起喂给 Claude：

````
请根据下面的「代码分析结果」和「建表 DDL」，生成 NL2SQL 语义层 YAML 文件。

要求：
1. 严格遵循下方的 YAML 格式规范
2. 枚举值优先使用「代码分析结果」中的定义（比 DDL COMMENT 更完整准确）
3. 中文名(display_name) 优先使用代码注解/i18n 中的中文，其次从 DDL COMMENT 推断
4. 敏感列 = 代码分析中识别的敏感字段 + DDL 中明显的敏感列（身份证、卡号、IP 等）
5. skip_index = JSON 大字段、请求/响应体、内部技术 ID 等
6. relations 使用代码中实际存在的 JOIN 关系（不要猜测）
7. common_queries 参考代码中的实际查询模式，生成 5-6 条覆盖：
   - 计数/总量（COUNT）
   - 分组统计（GROUP BY）
   - 比率/占比
   - 时间范围过滤
   - 枚举值 CASE WHEN 翻译
   - 代码中高频出现的查询场景
8. tags 包含：表中文名关键词 + 业务术语 + 用户可能的口语表达
9. query_tips 参考代码中的常见过滤条件

代码分析结果：
<粘贴 Step 1 的输出>

建表 DDL：
```sql
<粘贴 SHOW CREATE TABLE 输出>
```

YAML 格式规范：
<粘贴下方第二节的格式规范>

参考示例：
<粘贴一个已有的 YAML 文件，如 pmt_account.yaml>
````

### Step 4: 人工审核

| 审核项 | 重点 | 常见问题 |
|--------|------|---------|
| **enum_values** | 对照代码枚举类，确认值和 label 完全一致 | 代码里有 10 个值，Claude 只提取了 8 个 |
| **relations** | 确认 target_table 和 target_column 正确 | 列名相似但实际关联不同表 |
| **common_queries SQL** | 在 Doris 上跑一遍 | 列名大小写、Doris 语法差异 |
| **sensitive** | 对照公司数据安全规范 | 遗漏业务特有的敏感字段 |
| **tags** | 补充团队口语/缩写 | Claude 不知道内部黑话 |
| **description** | 补充业务上下文 | DDL + 代码只能推断技术含义 |

### Step 5: 提交

文件放到 `semantic_layer/tables/<表名>.yaml`，重启服务自动生效。

## 二、YAML 格式规范

把这段规范喂给 Claude 作为生成约束：

```yaml
table:
  name: <表名>                    # 必填 | Doris 中的表名
  database: dwd_banking           # 必填 | 所在数据库
  display_name: <中文表名>         # 必填 | 简洁的中文名
  description: |                  # 必填 | 2-4 句话：记录什么？每行代表什么？
    这张表记录了......
    每行代表一条......
  tags: [标签1, 标签2, ...]        # 必填 | 用户搜索关键词，3-8 个，中英文都要
  query_tips: <查询注意事项>        # 选填 | 如「查询时需带 is_delete=0」

columns:
  # --- 业务关键列：需要中文名 / 枚举值 / 补充说明的列 ---
  - name: <列名>                  # 必填 | 与 DDL 一致
    display_name: <中文列名>       # 必填
    description: <补充说明>        # 选填 | 列名不够自解释时加
    enum_values:                  # 选填 | 有固定取值的列必须填
      - {value: 1, label: "含义"}
      - {value: 0, label: "含义"}

  # 字符串型枚举简写:
  # enum_values: [LOW, MEDIUM, HIGH]

  # --- 敏感列：不参与检索，不出现在 Prompt 中 ---
  - name: <列名>
    sensitive: true

  # --- 跳过索引列：不参与向量化，但保留在 DDL 中 ---
  - name: <列名>
    skip_index: true

  # 未列出的列：系统自动从 DDL 获取，不需要重复写

relations:                        # 选填
  - column: <本表列名>
    target_table: <目标表名>
    target_column: <目标表列名>
    join_type: LEFT JOIN
    description: <关联说明>

common_queries:                   # 必填 | 至少 3 条，建议 5-6 条
  - question: <自然语言问题>
    sql: |
      SELECT ...
      FROM dwd_banking.<表名>
      WHERE ...
    tables: [<涉及的表名>]
    difficulty: easy               # easy / medium / hard
```

**common_queries SQL 规范：**
- 必须是可直接执行的 Doris SQL
- 列别名用中文双引号：`COUNT(*) AS "数量"`
- 枚举值查询用 CASE WHEN 翻译成中文
- difficulty：单表简单聚合 = easy，CASE WHEN/多条件 = medium，多表 JOIN/窗口函数 = hard

## 三、业务术语（glossary）

如果表涉及业务专有名词，追加到 `semantic_layer/glossary/glossary.yaml`：

```yaml
glossary:
  - term: <术语>                  # 用户可能说的词
    definition: <一句话定义>
    sql_hint: "<对应 SQL 条件>"
    related_tables: [<表名>]
    related_columns: [<表名.列名>]
```

示例：
```yaml
  - term: VA账户
    definition: 虚拟账户（Virtual Account），account_bank_type = 1000
    sql_hint: "account_bank_type = 1000"
    related_tables: [pmt_account_bank_details]
    related_columns: [pmt_account_bank_details.account_bank_type]
```

术语也建议在 Step 1 扫描代码时一起提取，Claude 能从代码注释和常量命名中识别业务术语。

## 四、交付 Checklist

- [ ] YAML 文件放到 `semantic_layer/tables/<表名>.yaml`
- [ ] enum_values 与代码枚举类一致（**重点审核**）
- [ ] common_queries >= 3 条，SQL 已在 Doris 上验证可执行（**重点审核**）
- [ ] sensitive 标记所有敏感列（PII、密钥、卡号等）
- [ ] relations 的目标表/列确认正确（**重点审核**）
- [ ] 新术语已追加到 `glossary.yaml`
